# Unified Execution: current-state audit and migration plan

Status: preparatory design; no production cutover authorized
Target release: `INT-1 Execution Core`

This plan prepares the tasks:

- `Product / Repository / SecurityControl` — effort `L`;
- `Connector and ScannerInstance registry` — effort `L`;
- `Unified Execution / ExecutionStep lifecycle` — effort `XL`;
- `Artifact / Delivery / Provenance` — effort `L`;
- `Versioned ingestion API and event history` — effort `L`.

It does not change the current runtime before `INT-0 Baseline` passes its
exit criteria.

## Current-state audit

### Identity and targets

`products` and `repositories` are the common identity layer, but:

- repository uniqueness is not enforced by database constraint;
- a repository has no stable GitLab project ID or instance reference;
- GitLab identity is duplicated across pipeline, audit and IaC tables;
- product and repository configuration is mixed with ASOC synchronization
  fields;
- expected security controls and control bindings do not exist.

### Existing run stores

| Store | Granularity | Strengths | Gaps |
|---|---|---|---|
| `active_pipelines` | GitLab pipeline | Stable `(project_id, pipeline_id)` uniqueness, polling timestamps | Aggregate completion is not the outcome of each security control |
| `pipeline_jobs` | GitLab job | Upsert by GitLab job ID, raw job state and timing | No canonical failure reason or immutable transition history |
| `job_reports` | completed job report | Long-term dashboard metrics and raw payload side table | Direct ingestion creates duplicates; no source event idempotency key |
| `config_scan_runs` | product/scope scan | Simple queued/running/terminal lifecycle | No per-repository execution row, partial result or cancellation |
| `iac_scan_runs` | group or single-repo scan | Queue claim locking, partial verdict, cancellation | Group orchestration and repository executions share one lifecycle layer |
| `iac_scan_repositories` | repository work item | Separates finder, scan and ASOC upload strings | No common step/event model; delivery does not determine run success |
| `ptai_scans` | asynchronous PT AI scan | GitLab job uniqueness and ASOC correlation | Engine and ASOC evidence are collapsed into `asoc_status` |
| `audit_scan_runs` | coverage collection job | Tracks audit progress | Coverage observation is not a security-control execution |

### Existing idempotency

- Pipeline registration: unique `(project_id, pipeline_id)`.
- Pipeline job polling: unique `(active_pipeline_id, gitlab_job_id)`.
- PT AI capture: unique `gitlab_job_id`.
- IaC group/rescan creation: application-level duplicate guards and
  `FOR UPDATE SKIP LOCKED` queue claim.
- Job ingest API: no event key; repeated posts create additional
  `job_reports`.
- Config scan: no database-level duplicate or event key.

### Existing failure evidence

The application stores free-text `error_text`/`error_message` in most flows,
but does not consistently store:

- stable failure category and reason code;
- failed lifecycle step;
- retryability;
- raw source status separately from canonical status;
- correlation/event identity;
- immutable state transition evidence.

### Retention implications

Current retention deletes old run rows and their children. Unified event
history must have an explicit retention contract:

- execution summaries may be pruned while preserving the latest execution per
  control binding;
- event and artifact metadata cannot outlive the execution unless deliberately
  archived;
- physical artifact retention is separate from database metadata retention;
- audit coverage snapshots remain derived observations and should not cascade
  from execution deletion.

## Target model

The target schema uses application-managed string constants with database
check constraints. PostgreSQL enum types are avoided so new adapter statuses
do not require enum migrations; raw statuses remain unrestricted strings.

### `executions`

One row represents either:

- a `control` attempt against a target; or
- an `orchestration` parent grouping child executions.

Proposed fields:

```sql
CREATE TABLE executions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    public_id VARCHAR(36) NOT NULL UNIQUE,
    execution_kind VARCHAR(24) NOT NULL,
    parent_execution_id BIGINT REFERENCES executions(id) ON DELETE SET NULL,
    retry_of_execution_id BIGINT REFERENCES executions(id) ON DELETE SET NULL,
    security_control_id BIGINT REFERENCES security_controls(id) ON DELETE RESTRICT,
    product_id INTEGER REFERENCES products(id) ON DELETE SET NULL,
    repository_id INTEGER REFERENCES repositories(id) ON DELETE SET NULL,
    status VARCHAR(32) NOT NULL,
    trigger_type VARCHAR(32) NOT NULL,
    source_system VARCHAR(32) NOT NULL,
    source_scope VARCHAR(255) NOT NULL DEFAULT 'default',
    source_execution_id VARCHAR(255),
    source_parent_id VARCHAR(255),
    target_ref VARCHAR(255),
    commit_sha VARCHAR(64),
    contract_snapshot JSONB NOT NULL DEFAULT '{}'::jsonb,
    raw_status VARCHAR(64),
    error_category VARCHAR(32),
    error_reason VARCHAR(64),
    error_step VARCHAR(64),
    error_retryable BOOLEAN,
    error_detail TEXT,
    requested_at TIMESTAMPTZ,
    queued_at TIMESTAMPTZ,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    last_event_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CHECK (execution_kind IN ('control', 'orchestration')),
    CHECK (status IN (
        'requested', 'queued', 'running', 'delivering',
        'cancel_requested', 'succeeded', 'partial', 'failed', 'cancelled'
    )),
    CHECK (execution_kind <> 'control' OR security_control_id IS NOT NULL)
);

CREATE UNIQUE INDEX uq_executions_source_identity
    ON executions(source_system, source_scope, source_execution_id)
    WHERE source_execution_id IS NOT NULL;

CREATE INDEX ix_executions_target_time
    ON executions(repository_id, created_at DESC);

CREATE INDEX ix_executions_parent
    ON executions(parent_execution_id, created_at);

CREATE INDEX ix_executions_status_time
    ON executions(status, last_event_at);
```

`contract_snapshot` freezes the obligations used to calculate the result, for
example required steps, required deliveries, scanner profile and freshness
window. Later policy changes must not rewrite historical outcomes.

### `execution_steps`

```sql
CREATE TABLE execution_steps (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    execution_id BIGINT NOT NULL REFERENCES executions(id) ON DELETE CASCADE,
    step_key VARCHAR(64) NOT NULL,
    ordinal INTEGER NOT NULL,
    attempt INTEGER NOT NULL DEFAULT 1,
    status VARCHAR(32) NOT NULL,
    source_system VARCHAR(32),
    source_step_id VARCHAR(255),
    raw_status VARCHAR(64),
    error_category VARCHAR(32),
    error_reason VARCHAR(64),
    error_retryable BOOLEAN,
    error_detail TEXT,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (execution_id, step_key, attempt),
    CHECK (status IN (
        'requested', 'queued', 'running', 'succeeded',
        'failed', 'cancelled', 'skipped'
    ))
);
```

### `artifacts`

```sql
CREATE TABLE artifacts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    execution_id BIGINT NOT NULL REFERENCES executions(id) ON DELETE CASCADE,
    produced_by_step_id BIGINT REFERENCES execution_steps(id) ON DELETE SET NULL,
    artifact_kind VARCHAR(64) NOT NULL,
    format VARCHAR(32),
    storage_uri TEXT,
    checksum_sha256 VARCHAR(64),
    size_bytes BIGINT,
    is_empty BOOLEAN,
    source_artifact_id VARCHAR(255),
    metadata_json JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

The database stores metadata and provenance. Large SARIF/JSON bodies remain in
object/file storage.

### `deliveries`

```sql
CREATE TABLE deliveries (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    execution_id BIGINT NOT NULL REFERENCES executions(id) ON DELETE CASCADE,
    artifact_id BIGINT REFERENCES artifacts(id) ON DELETE SET NULL,
    connector_instance_id BIGINT NOT NULL REFERENCES connector_instances(id) ON DELETE RESTRICT,
    required BOOLEAN NOT NULL DEFAULT TRUE,
    status VARCHAR(32) NOT NULL,
    destination_ref VARCHAR(255),
    external_delivery_id VARCHAR(255),
    idempotency_key VARCHAR(255) NOT NULL,
    raw_status VARCHAR(64),
    error_category VARCHAR(32),
    error_reason VARCHAR(64),
    error_retryable BOOLEAN,
    error_detail TEXT,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    confirmed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (connector_instance_id, idempotency_key),
    CHECK (status IN (
        'pending', 'delivering', 'succeeded', 'failed', 'cancelled', 'skipped'
    ))
);
```

### `execution_events`

```sql
CREATE TABLE execution_events (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    execution_id BIGINT NOT NULL REFERENCES executions(id) ON DELETE CASCADE,
    execution_step_id BIGINT REFERENCES execution_steps(id) ON DELETE CASCADE,
    delivery_id BIGINT REFERENCES deliveries(id) ON DELETE CASCADE,
    source_system VARCHAR(32) NOT NULL,
    source_scope VARCHAR(255) NOT NULL DEFAULT 'default',
    source_event_id VARCHAR(255) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    raw_status VARCHAR(64),
    occurred_at TIMESTAMPTZ NOT NULL,
    observed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payload_json JSONB NOT NULL DEFAULT '{}'::jsonb,
    UNIQUE (source_system, source_scope, source_event_id)
);

CREATE INDEX ix_execution_events_timeline
    ON execution_events(execution_id, occurred_at, id);
```

Payloads must be sanitized before persistence. Tokens, authorization headers,
scanner secrets and complete sensitive logs are prohibited.

## Migration strategy

### Phase 0 — contract freeze

- Confirm control vocabulary and mandatory delivery obligations.
- Validate lifecycle/taxonomy against customer failure stories.
- Freeze canonical status/reason constants for v0.2.

No database migration is applied in this phase.

### Phase 1 — additive schema

- Add Product/Repository/SecurityControl and connector registry foundations.
- Add execution tables, indexes and constraints.
- Do not change existing writers or readers.
- Add retention support for the new tables, disabled until cutover.

Rollback: drop only empty new tables in reverse dependency order.

### Phase 2 — historical backfill

Run idempotent batches with a durable checkpoint:

1. `active_pipelines` become orchestration executions.
2. Security `pipeline_jobs` become child control executions; non-control jobs
   become parent steps.
3. Unmatched historical `job_reports` become imported terminal control
   executions using a deterministic source identity.
4. `iac_scan_runs` become orchestration parents, except single-repository runs.
5. `iac_scan_repositories` become child control executions with finder,
   scanner and delivery steps.
6. `config_scan_runs` become executions; project-level detail is represented
   only where evidence exists—no synthetic success rows.
7. `ptai_scans` become control executions with trigger, ASOC orchestration,
   engine and confirmation steps.

Backfill rules:

- deterministic `source_execution_id` prevents duplicates;
- missing evidence maps to `raw_status = unknown`, never invented timestamps;
- current successful IaC scans with unconfirmed required ASOC delivery map to
  `partial` or `failed` according to the frozen contract;
- `stale` pipeline rows retain their last known lifecycle state plus a stale
  condition event;
- backfill commits in bounded batches and can resume safely.

Rollback: new rows may be deleted by `source_system` and backfill version;
legacy tables remain authoritative.

### Phase 3 — dual write

- Existing services continue writing legacy tables.
- A single lifecycle service writes execution state/events in the same
  transaction where possible.
- External event ingestion uses versioned idempotency keys.
- Shadow reconciliation compares legacy and unified outcomes.

Required gate:

- no duplicate execution for replayed events;
- no terminal-to-running regressions;
- outcome parity is explainable for every mismatch;
- new writes do not change current UI behavior.

Rollback: disable unified dual write via feature flag; legacy path remains
unchanged.

### Phase 4 — read shadow and cutover

- Build Target 360 using unified reads behind a feature flag.
- Compare counts, latest state, durations and links with legacy screens.
- Switch operational timeline reads only after reconciliation passes.
- Keep legacy writes during one observation window.

Rollback: restore legacy read flag.

### Phase 5 — legacy retirement

- Stop legacy writes only after all current adapters use the versioned event
  contract.
- Preserve compatibility views if existing reports still query legacy shapes.
- Remove legacy tables in a separate release after retention and restore tests.

No destructive migration belongs in the initial v0.2 cutover.

## Backfill identity map

| Source | Deterministic identity |
|---|---|
| GitLab pipeline parent | `gitlab:pipeline:{instance}:{project_id}:{pipeline_id}` |
| GitLab job control | `gitlab:job:{instance}:{gitlab_job_id}` |
| Direct job report | `legacy:job_report:{job_report_id}` |
| IaC run parent | `scanops:iac_run:{iac_scan_run_id}` |
| IaC repository child | `scanops:iac_repo:{iac_scan_repository_id}` |
| Config scan | `scanops:config_run:{config_scan_run_id}` |
| PT AI scan | `asoc:ptai:{gitlab_job_id}` |

The GitLab instance must be included wherever project/job IDs are not globally
unique across configured instances.

## Operational safety checklist

- Additive migrations use `IF NOT EXISTS` where appropriate.
- Large indexes are created with a production-safe deployment procedure.
- Backfill has batch size, checkpoint, dry-run and mismatch report.
- Every write path has an explicit idempotency key.
- Secrets are redacted before event persistence.
- Retention protects active, cancel-requested and latest-per-binding rows.
- Restore rehearsal includes execution events and artifact metadata.
- Feature flags independently control dual write and unified reads.
- Legacy tables remain untouched until a later removal release.
